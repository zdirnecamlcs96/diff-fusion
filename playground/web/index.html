diff-fusion · playground

Define a policy, paste two systems' data, watch reconciliation happen stage by stage.

How to use this playground

The five inputs

  • System A / System B — raw JSON from each system. Shapes can differ.
  • Schema — cif_schema (target fields) + transformations.<format> (how each system's JSON maps into the CIF).
  • Policy — per-field merge rules. See reference below.
  • Ancestor — the last-synced canonical state. Leave blank for a first sync.
  • System A / B name — must match both schema.transformations.<name> and any owned_by.system in the policy.

Policy reference

{
  "per_field": {
    "price":     { "kind": "owned_by", "system": "erp" },
    "qty_recv":  { "kind": "additive" },
    "tags":      { "kind": "append" },
    "po_status": {
      "kind": "state_machine",
      "transitions": [
        { "from": "open", "to": "closed" }
      ]
    }
  }
}

Supported kind:

  • owned_by — one system wins; other side's change reverts. Requires system.
  • additive — numeric counters; both sides' deltas vs ancestor accumulate.
  • append — arrays; both sides' additions concatenate. (Does not dedupe.)
  • state_machine — enum fields; only listed (from, to) transitions pass. Requires transitions.
  • set_by_key — arrays of objects. Elements are matched across systems by an identity that is either a single field name or a composite (array of field names, e.g. ["sku", "uom"]). Stable anchors a_anchor / b_anchor are required: each side's own local primary key (e.g. externalId / internalId) so rows that mutate an identity field still re-home to their original ancestor row. Optional on_both_changed: escalate (default), union (shallow-merges fields), prefer_a, prefer_b. Optional nested: a map of field name → sub-set_by_key declaration; each named field is recursively merged as its own keyed array so per-line detail inside a matched parent element (e.g. fulfillment.items[]) survives the merge instead of being overwritten wholesale.

Fields not listed that changed on both sides produce a NoPolicy conflict.

Schema-declared array element shapes

Array fields in cif_schema can declare their per-element shape with an element block. Element fields marked with anchor: "a" or anchor: "b" become structural anchors that a set_by_key policy can verify against at build time — the playground rejects misaligned configs before running any sync. The element block also tells the transformer to walk source arrays and emit per-element CIF objects (rather than passing arrays through opaquely):

"items": {
  "type": "array",
  "element": {
    "externalId": { "type": "string", "anchor": "a" },
    "internalId": { "type": "string", "anchor": "b" },
    "sku":        { "type": "string" },
    "uom":        { "type": "string" },
    "qty":        { "type": "number" }
  }
}

Each side's transformation block then carries a matching element map with per-field source_path entries, so a side with only externalId (and no internalId yet) produces CIF elements with just its own anchor. The anchor-rehoming matcher takes it from there.

Array merges: the anchor rule

Every set_by_key policy must declare both a business identity and a per-side stable anchor. Anchors aren't optional: in every real integration, one system hands out immutable local IDs while business fields (SKU, UOM, line number) stay editable. Without an anchor, a rename shows up as a remove-plus-add and corrupts three-way diffing.

  1. Business identity (identity) — a field or tuple of fields that both systems populate and that uniquely name a row: sku, or (sku, uom), or (sku, uom, lot). Use a composite when the same sku can appear on multiple lines with different configurations.
  2. Per-system stable anchors (a_anchor / b_anchor) — each side's own local primary key (e.g. externalId on A, internalId on B). The ancestor stores both anchors, so the policy can re-home each incoming row to its ancestor row via the anchor before composite-identity matching runs.

Row-level nuance: individual elements may not carry an anchor value yet (e.g. a row A just created that hasn't roundtripped to B). That's fine — those rows fall through to composite-identity matching automatically. The rule is that the policy declaration must name the anchor fields; missing values per-row are handled gracefully.

Cross-system items — worked example

System A (external) tags rows with externalId, System B (internal) with internalId. They share sku + uom as the business identity. The policy needs both:

"items": {
  "kind": "set_by_key",
  "identity": ["sku", "uom"],
  "a_anchor": "externalId",
  "b_anchor": "internalId",
  "on_both_changed": "union"
}

on_both_changed controls how matched-but-divergent rows resolve. union does a shallow field-merge, so both externalId (from A) and internalId (from B) end up linked on the same merged record. Other modes: prefer_a, prefer_b, escalate.

The seeded sample exercises the identity-mutation path. A bumps the qty on (SKU-100, BTL) and renames (SKU-100, CTN) to (SKU-100, BOX); B does nothing; the anchor re-homing keeps the renamed row linked. The final merged record looks like:

[
  { "sku": "SKU-100", "uom": "BTL", "qty": 12,
    "externalId": "A-L1", "internalId": "B-I1" },
  { "sku": "SKU-100", "uom": "BOX", "qty": 2,
    "externalId": "A-L2", "internalId": "B-I2" },
  { "sku": "SKU-300", "uom": "BTL", "qty": 3,
    "externalId": "A-L9" }              // new in A, no B row yet
]

Try switching on_both_changed to prefer_a to see B's internalId drop out, or to escalate for the conflict path. For per-line nested reconciliation (e.g. items inside a matched fulfillment), add a nested block:

"items": {
  "kind": "set_by_key",
  "identity": ["sku", "uom"],
  "a_anchor": "externalId",
  "b_anchor": "internalId",
  "on_both_changed": "union",
  "nested": {
    "subLines": {
      "kind": "set_by_key",
      "identity": "sku",
      "a_anchor": "externalId",
      "b_anchor": "internalId"
    }
  }
}

The pipeline stages

  1. Transform A → CIF + Transform B → CIF — run in parallel on the backend (tokio::spawn_blocking + tokio::join!); animate together as one step.
  2. 3-way Diff — A vs Ancestor, B vs Ancestor, A vs B. Blank ancestor is treated as {}.
  3. Policy Resolution — dry-run. Shows would_write and any conflicts that would escalate.
  4. Outcome — real sync. One of Synced, Escalated, NoOp.

Reading the field changelog

Below the pipeline, successful syncs produce a per-field table. Each row is one CIF field that actually changed.

  • Policy column names the rule that governed this field (e.g. owned_by(erp), additive, set_by_key). For set_by_key it also lists the identity fields, both anchors, and the on_both_changed strategy, so the row-level behaviour is explainable at a glance.
  • Ancestor / System A / System B / Written columns render the value as a git-style line diff vs the ancestor. Unchanged lines show dim; + additions are green, - removals are red. Multi-line values (like items) show each JSON field on its own row, so you can see exactly which sub-field flipped.
  • The cell for whichever side's value ended up winning is highlighted (green left border).
  • set_by_key digest — for array fields governed by set_by_key, the Written cell also shows a per-row status breakdown: [changed-in-a], [added-in-b], [removed-both], etc. When a side mutated an identity field, the row is tagged with (A re-homed via <anchor>) so the anchor path is visible, not just the resulting value.
  • Winner column names the source: <system name>, both, no-op, or derived. For numeric additive fields, a hint underneath shows the arithmetic, e.g. 5 + 1 + 2 for ancestor + (A−delta) + (B−delta) = 8.

Escalated outcomes replace the table with a conflict list color-coded by class: NoPolicy (gray), PolicyConflict (amber), InvariantViolation (red).

Quick recipes

  • Trigger a conflict — change state_machine.transitions to only allow draft → open. The seeded data drifts to closed from open, so the rule rejects it.
  • First sync — clear the Ancestor field entirely.
  • NoPolicy — delete "price" from per_field; both sides changed it, no rule → conflict.
  • Swap owner — change owned_by.system from "erp" to "inv", or rename via the name inputs.
  • Watch anchor re-homing — the seeded sample already mutates an identity field (uom: CTN → BOX on one line). Watch the items row in the changelog: the renamed line stays linked to its ancestor instead of showing up as a remove-plus-add. Remove a_anchor or b_anchor from the declaration to see the server reject the payload with a validation error.
  • Switch merge behavior — cycle on_both_changed through union / prefer_a / prefer_b / escalate on the items policy and watch the Winner column change.
