diff-fusion · playground

Define a policy, paste two systems' data, watch reconciliation happen stage by stage.

How to use this playground

The five inputs

  • System A / System B — raw JSON from each system. Shapes can differ.
  • Schema — cif_schema (target fields) + transformations.<format> (how each system's JSON maps into the CIF).
  • Policy — per-field merge rules. See reference below.
  • Ancestor — the last-synced canonical state. Leave blank for a first sync.
  • System A / B name — must match both schema.transformations.<name> and any owned_by.system in the policy.

Policy reference

{
  "per_field": {
    "price":     { "kind": "owned_by", "system": "erp" },
    "qty_recv":  { "kind": "additive" },
    "tags":      { "kind": "append" },
    "po_status": {
      "kind": "state_machine",
      "transitions": [
        { "from": "open", "to": "closed" }
      ]
    }
  }
}

Supported kind:

  • owned_by — one system wins; other side's change reverts. Requires system.
  • additive — numeric counters; both sides' deltas vs ancestor accumulate.
  • append — arrays; both sides' additions concatenate. (Does not dedupe.)
  • state_machine — enum fields; only listed (from, to) transitions pass. Requires transitions.
  • set_by_key — arrays of objects. Elements are matched across systems by an identity that is either a single field name or a composite (array of field names, e.g. ["sku", "uom"]). Optional stable anchors a_anchor / b_anchor give each side a per-row primary key (e.g. externalId / internalId) so rows that mutate an identity field still re-home to their original ancestor row. Optional on_both_changed: union (default — shallow-merges fields), prefer_a, prefer_b, escalate.

Fields not listed that changed on both sides produce a NoPolicy conflict.

Array merges: the anchor rule

When you merge an array, the policy MUST name at least one unique anchor per row. Without an anchor, the engine has no way to know which A-row corresponds to which B-row, so it either duplicates everything (append) or escalates.

An anchor can take either of two shapes — most real reconciliations need both:

  1. Business identity (identity, required) — a field or tuple of fields that both systems populate and that uniquely name a row: sku, or (sku, uom), or (sku, uom, lot), etc. This is what tells the engine A-row X "is" B-row Y. Use a composite when the same sku can appear on multiple lines with different configurations.
  2. Per-system stable anchors (a_anchor / b_anchor, optional) — each side's own local primary key (e.g. externalId on A, internalId on B). Required whenever an identity field can mutate (someone renames uom, moves a lot, changes a warehouse). The ancestor stores both anchors, so the policy can re-home each incoming row to its ancestor row via the anchor before composite-identity matching runs.

Cross-system items — worked example

System A (external) tags rows with externalId, System B (internal) with internalId. They share sku + uom as the business identity. The policy needs both:

"items": {
  "kind": "set_by_key",
  "identity": ["sku", "uom"],
  "a_anchor": "externalId",
  "b_anchor": "internalId",
  "on_both_changed": "union"
}

on_both_changed controls how matched-but-divergent rows resolve. union does a shallow field-merge, so both externalId (from A) and internalId (from B) end up linked on the same merged record. Other modes: prefer_a, prefer_b, escalate.

The seeded sample exercises the identity-mutation path. A bumps the qty on (SKU-100, BTL) and renames (SKU-100, CTN) to (SKU-100, BOX); B does nothing; the anchor re-homing keeps the renamed row linked. The final merged record looks like:

[
  { "sku": "SKU-100", "uom": "BTL", "qty": 12,
    "externalId": "A-L1", "internalId": "B-I1" },
  { "sku": "SKU-100", "uom": "BOX", "qty": 2,
    "externalId": "A-L2", "internalId": "B-I2" },
  { "sku": "SKU-300", "uom": "BTL", "qty": 3,
    "externalId": "A-L9" }              // new in A, no B row yet
]

Try switching on_both_changed to prefer_a to see B's internalId drop out, or to escalate for the conflict path. Delete a_anchor / b_anchor to see the anchor breakdown when A renames uom: the old (SKU-100, CTN) line re-appears via B and a new (SKU-100, BOX) line is added from A with only A's ID.

The pipeline stages

  1. Transform A → CIF + Transform B → CIF — run in parallel on the backend (tokio::spawn_blocking + tokio::join!); animate together as one step.
  2. 3-way Diff — A vs Ancestor, B vs Ancestor, A vs B. Blank ancestor is treated as {}.
  3. Policy Resolution — dry-run. Shows would_write and any conflicts that would escalate.
  4. Outcome — real sync. One of Synced, Escalated, NoOp.

Reading the field changelog

Below the pipeline, successful syncs produce a per-field table. Each row is one CIF field that actually changed.

  • Ancestor / System A / System B / Written columns render the value as a git-style line diff vs the ancestor. Unchanged lines show dim; + additions are green, - removals are red. Multi-line values (like items) show each JSON field on its own row, so you can see exactly which sub-field flipped.
  • The cell for whichever side's value ended up winning is highlighted (green left border).
  • Winner column names the source: <system name>, both, no-op, or derived. For numeric additive fields, a hint underneath shows the arithmetic, e.g. 5 + 1 + 2 for ancestor + (A−delta) + (B−delta) = 8.

Escalated outcomes replace the table with a conflict list color-coded by class: NoPolicy (gray), PolicyConflict (amber), InvariantViolation (red).

Quick recipes

  • Trigger a conflict — change state_machine.transitions to only allow draft → open. The seeded data drifts to closed from open, so the rule rejects it.
  • First sync — clear the Ancestor field entirely.
  • NoPolicy — delete "price" from per_field; both sides changed it, no rule → conflict.
  • Swap owner — change owned_by.system from "erp" to "inv", or rename via the name inputs.
  • See the anchor rule break — remove a_anchor / b_anchor from the items policy; A's uom rename now orphans the line.
  • Switch merge behavior — cycle on_both_changed through union / prefer_a / prefer_b / escalate on the items policy and watch the Winner column change.
